The problem

  • APIs are now bought by programs: apps, bots, AI agents, indexers. They want to pay per call, cents or less.
  • API keys + monthly plans don't fit a client that needs 40 calls today and none tomorrow.
  • "Pay first" protocols (HTTP 402 / x402) move money but give the buyer no recourse when the call fails.
  • And no way to know, before paying, whether a provider actually delivers.
What a machine buyer needs
price up front · pay only for what is served · automatic refund when it isn't · a public track record of the seller

Prepaid sessions

  1. Open once: the payer locks a budget and can name a fresh session key: an agent can spend this budget and nothing else
  2. Every request is a signed voucher, not a transaction. The seller checks signature, budget, count and chain before the handler runs
  3. Each voucher commits to the hash of the previous response. A redeemed batch is signed by the session key, not claimed by the provider
  4. One Ethereum transaction settles many sessions across both VMs: redeem in Solidity, record in ink!, all or nothing
  5. Failed request: not charged. Lost response: replayed free.
  6. Anyone can replay the public log against the chain: ACCEPT or REJECT, with every check listed
Portal Meter · Swift Bot Labs4

Per-request escrow, for calls worth more

  1. GET → 402 with a quote (price, token, endpoint, nonce)
  2. Client pays one request into escrow: MeterSettlement.pay() on Portaldot's EVM; the request id is bound to the payer on-chain
  3. Client retries with a signed proof → served once, with a provider-signed receipt
  4. Provider settles or refunds; the buyer can reclaim after a delay if the provider does nothing
  5. The outcome is anchored in an ink! registry in the same transaction; buyers confirm or dispute

Why Portaldot is essential

Native assets are ERC-20s

Every pallet-assets token is reachable from Solidity at a precompile address. Endpoints are priced in a native asset; no wrapped token to deploy or trust.

Two VMs, one identity

Escrow in Solidity (pallet-revive), provider registry in ink! (pallet-contracts). Both sides key accounts by the same EVM address, using the runtime's own mapping rule.

One transaction across both VMs

An Ethereum transaction to the runtime pallets address carries utility.batchAll([revive.call(settle), contracts.call(record)]): settlement and anchor succeed or fail together. A single-VM chain cannot do this.

Ink! checks EVM payers natively

The registry recomputes the Solidity request id (keccak + ABI) from the caller's address, so only the real payer can rate a request, with no bridge or oracle.

Who pays, and how it grows

  • Users: data and API providers on Portaldot (indexers, RPC and analytics services, AI tool endpoints) and the apps and agents that call them.
  • First product, live: the paid Portaldot data API, 0.01 pUSD per call, priced in Portaldot's own test dollar, so any builder can buy with real testnet funds.
  • Revenue (planned): a small protocol fee on settlement (basis points, not in the testnet contracts yet) and a hosted seller for providers who do not want to run one. The Worker already shows what that service is.
  • Growth: a few lines to add to any API (Express, Workers, Bun, Deno), then one command to register. Listing in the Portaldot ecosystem directory, wallet support for 402 quotes.
Honest status
Traffic so far is our own measurement key and visitors of the live page. No user demand is claimed. The next milestone is a second provider.
