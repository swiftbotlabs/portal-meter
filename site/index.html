A cent per API call. A hundred calls per transaction.

If you run an API, Portal Meter lets AI agents pay you a cent per call on Portaldot, and you settle more than a hundred calls in one transaction instead of paying a fee on each one.

Paying on-chain for each call locked 7.53 tPOT for good. A session locks 0.076 per call.

On Portaldot every new storage slot locks a deposit. One paid request left 7.53 tPOT locked against a price of 0.025 test dollars: fine for a call worth a few cents, fatal for one worth a fraction of a cent. So we built prepaid sessions.

Open once. Pay every call with a signature. Settle many in one transaction.

No transaction per request, and no trust in the seller's word: every batch it redeems carries the buyer's own signature over the requests made and the responses received.

    Open a session once

    The payer locks a budget in MeterSession. It can name a fresh session key, so an agent holds a key that can spend this budget and nothing else. Every pallet-assets token is reachable from Solidity at a precompile address: the hosted seller is priced in pUSD, asset 7777, Portaldot's own test dollar.

  2. 2

    Every call is a signed voucher

    HTTP 402 with a price, a voucher signed by the client, HTTP 200 with the data. Each voucher commits to the hash of the previous response, so the vouchers form a chain the seller cannot rewrite.

    402GET /v1/asset/77770.01 pUSD
    sigvoucher 1, signedno gas
    200GET + voucherdata + receipt
    head[n] = keccak256(head[n-1], request[n], response[n-1])
  3. 3

    One transaction settles many

    One Ethereum transaction carries utility.batchAll: the money moves in Solidity and the public record lands in ink!, together or not at all, for many sessions at once. An Ethereum-signed transaction to the runtime pallets address dispatches revive.call and contracts.call together; a single-VM chain would need a bridge or a second transaction.

    1 Ethereum txutility.batchAll
    EVMMeterSession.redeempallet-revive, the money
    WASMMeterRegistry.recordpallet-contracts, the public record
    × each session in the batch

From HSK Meter (Oct 2026, HashKey Chain, MIT), as patterns rewritten here, no file copied: the x402-style payment headers, a request id bound to its payer, the provider refund and single-use request id, the endpoint record, and the escrow seller's quote, pay and retry flow.

What each side can and cannot do.

"Contract" means the deployed MeterSession, MeterSettlement and MeterRegistry. Off-chain parts are named as off-chain.

A malicious seller

Cannot, enforced by the contract

  • Take more than the buyer's session key signed: redeem checks the signature, caps the total at the budget and accepts only newer vouchers.
  • Touch the unspent budget: only the payer may close.
  • Redeem a session of an endpoint it does not run, or switch the token.

Can, and what limits it

  • Take one price for a request it never answers, because each voucher is signed before its response exists. The client stops signing at the first bad receipt.
  • Serve wrong data: a redeemed head proves which bytes the client accepted, not that they were good.

A malicious buyer

Cannot, enforced by the contract

  • Close before 15 minutes after expiry, which leaves the seller time to redeem.
  • Take back redeemed money, reopen a closed session or replay its vouchers.
  • Spend past the budget, or make the seller pay the session's storage.

Can, and what limits it

  • Stop at any time: the seller risks only what it has not redeemed, and it holds a signed voucher for every request it answered.
  • Open many small sessions: the hosted seller refuses budgets under 0.25 pUSD (off-chain).

Refunds: close after expiry returns the unspent budget plus most of the storage deposit (7.67 tPOT measured). A failed request is not charged and a lost response is sent again for free, by seller code. Full model: Sessions: protocol, guarantees and limits and Security.

Add it to your API

  • Node.js
  • Cloudflare Workers
  • Bun
  • Deno
  • Express

The metering core works on Web standard Request and Response, so it runs on Node.js, Cloudflare Workers, Bun and Deno, with an adapter for Express. Register an endpoint on both VMs with one command, wrap a handler, done. The hosted seller is itself built on it.

Reuse, tested: a second seller in a folder of its own, built on the published entry points only, live as endpoint 4 at paid-indexer.swiftbotlab.workers.dev.

server.mjs
import { createMeter, metered } from 'portal-meter';

const meter = createMeter({ chainId, sessionContract, endpointId, wallet, token, tokenSymbol, decimals, readSession });

// Express: the handler returns the body, the meter hashes and signs it
app.get('/v1/weather/:city', metered(meter, { price: 10_000n }, async req => forecast(req.params.city)));

// Cloudflare Workers, Bun, Deno, Hono: Web standard Request and Response
export default { fetch: req => meter.charge(req, { price: 10_000n }, () => forecast('oslo')) };
